Notes
----------------------------------------------------------------------
- All samples are designed for the OMTF overlap acceptance, roughly |eta| in
  the 0.8 to 1.24 band for the overlap-focused multi-muon samples.
- The prompt single-muon and displaced single-muon samples use full phi to
  avoid imposing processor-window bias.
- The same-window samples restrict phi intentionally to ensure multiple muons
  occupy the same OMTF processor region.
- The NanoAOD output contains OMTF candidates, propagated gen muons, and GMT
  stub tables; the omtf_hits output contains the OMTF-region input stub data
  needed for ML training and full replacement studies.

GMT-VISIBLE-STUB CAMPAIGN (G1-G10)
======================================================================
Additional campaign targeted at the Phase-B GMT-visible-stub branch.
Does NOT replace existing S/B samples.

Goal: Reconstruct OMTF-overlap-region muon candidates using GMT-visible
KMTF/TPS-like stub inputs, while suppressing out-of-domain barrel tracks
and PU backgrounds.

Known issues addressed:
- B2 false second candidate from PU (addressed by G2/G4/G8)
- Out-of-domain low-eta tracks firing (addressed by G7/G8)
- Out-of-domain high-eta endcap tracks firing (addressed by G9/G10)
- Weak slot-2 efficiency under PU (addressed by G6)
- Weak displaced PU handling (addressed by G4/G5)

Naming convention:
- G* = GMT-visible-stub campaign datasets
- No-PU: G1, G3, G7, G9_pos, G9_neg
- PU200: G2, G4, G5, G6, G8, G10_pos, G10_neg

Fragment safety rules enforced:
- Single-muon samples (G1/G2/G3/G4/G7/G8/G9_pos/G9_neg/G10_pos/G10_neg): exactly ONE entry in PartID
- etaFilter defined iff 0.82 <= |eta| <= 1.24 overlap required
- etaFilter MUST appear in ProductionFilterSequence if defined
- AddAntiParticle = False for all G-campaign fragments

Pre-production audit scripts:
  scripts/audit/check_fragments_static.py   (static fragment check)
  scripts/audit/audit_gen_particles.py      (gen-level check after test run)
  scripts/omtf_gmt/audit_domain_mismatch.py (stub-level domain check)

Submit files:
  condor/G1.sub through condor/G10_neg.sub (individual)
  condor/GMT_overlap_production.sub        (grouped, all 5200 jobs)

DISPLACED-MUON ML STUDY CAMPAIGN (C-series + G13-G17 extensions)
======================================================================
This campaign supports the Big Displaced-Muon ML Trigger Study
(new_datset_reqs.md). The goal is to build a dedicated ML-based
displaced-muon recovery path for the CMS overlap region.

Central metric:
  incremental_displaced_recovery = efficiency(OMTF OR ML) - efficiency(OMTF)

All C-series samples use:
  - Gun: FlatRandomPtGunProducer2
  - Spectrum: flat in 1/pT
  - Eta: OMTF overlap 0.82 < |eta| < 1.24 (enforced by etaFilter)
  - Phi: full 2pi
  - RandomCharge: True (both charges)
  - CMSSW: 14.2.0_pre2, Phase2C17I13M9, Extended2026D110, 140X_mcRun4_realistic_v4

C-series already produced (C1-C16):
  C1-C6:   prompt pT bins (2-5, 5-10, 10-20, 20-50, 50-100, 100-200 GeV), no PU
  C7-C12:  displaced (|d0| 0.2-50 cm) same pT bins, no PU
  C13-C14: prompt pT 2-5, 5-10 GeV, PU200
  C15-C16: displaced pT 2-5, 5-10 GeV, PU200

C-series new additions (C17-C28):
  C17-C20: prompt pT 10-20, 20-50, 50-100, 100-200 GeV, PU200  (WP5 coverage)
  C21-C24: displaced pT 10-20, 20-50, 50-100, 100-200 GeV, PU200 (WP5 recovery)
  C25-C26: mild-displaced (|d0| 0.05-0.2 cm) pT 2-5, 5-10 GeV, no PU  (WP4 ambiguity)
  C27-C28: mild-displaced (|d0| 0.05-0.2 cm) pT 2-5, 5-10 GeV, PU200  (WP4/WP5 ambiguity)

G-series extensions (G13-G17) — condor .sub files added:
  G13_pos/neg:  prompt transition guard |eta| 1.2-1.6, no PU
  G14_pos/neg:  prompt transition guard |eta| 1.2-1.6, PU200
  G15_pos/neg:  prompt endcap control |eta| 1.6-2.4, no PU
  G16_pos/neg:  prompt endcap control |eta| 1.6-2.4, PU200
  G17:          two displaced muons, overlap region, no PU

Datasets with condor .sub missing prior to this campaign:
  G13_pos, G13_neg, G14_pos, G14_neg, G15_pos, G15_neg,
  G16_pos, G16_neg, G17

PU200 TRUTH-PERSISTENCE DESIGN NOTE
======================================================================
Scope:
- This note fixes the design for adding pileup-muon truth persistence to
  OMTFAllInputTree without breaking existing ROOT consumers.
- The implementation target is additive. Existing branches and old files must
  remain readable without reinterpretation.

Motivation:
- Current `reg_stub_trackId` encodes only hard-scatter GenMuon truth:
  - 0 = no matched truth / noise
  - 1..K = index in `GenMuon_*`
- That scheme cannot represent real pileup muons, because `GenMuon_*` is a
  hard-scatter table and does not cover pileup TrackingParticles.
- Source inspection already showed that `CandidateSimMuonMatcher.cc` contains a
  TrackingParticle-based path intended for minbias / pileup use. The missing
  piece is wiring that truth into `DataROOTDumper2AllInput.cc` persistence.

Branch-level design:
- Do NOT change the meaning of `reg_stub_trackId`.
- Add a parallel branch `reg_stub_tpId` with the semantics:
  - 0 = no matched pileup-muon truth
  - 1..M = index in a new per-event `TpMuon_*` table
- Add a new `TpMuon_*` table containing only selected TrackingParticle muons:
  - `TpMuon_pt`
  - `TpMuon_eta`
  - `TpMuon_phi`
  - `TpMuon_charge`
  - `TpMuon_dxy`
  - `TpMuon_lxy`
  - `TpMuon_eventId`
  - `TpMuon_bunchCrossing`
- `TpMuon_eventId` and `TpMuon_bunchCrossing` are mandatory, because they make
  in-time vs out-of-time pileup truth explicit and support BX-audit closure
  directly from truth labels.

Selection policy for `TpMuon_*` persistence:
- Persist only TrackingParticle muons (`|pdgId| == 13`).
- Apply a low-pT floor tuned for relevance and tuple size control:
  - baseline request: `pT > 1.5 GeV`
  - acceptable fallback if configuration simplicity is preferred: `pT > 2 GeV`
- Restrict acceptance to the overlap task plus guard band:
  - `|eta| < 1.6`
- Do not persist all TrackingParticles from PU200 events. The full population is
  too large and would inflate ntuple size and job memory for little training
  value.

Mixing / production precondition:
- The pilot must explicitly verify that the mixing configuration preserves the
  pileup SimTrack / SimVertex information needed by the TrackingParticle path.
- With classic mixing from GEN-SIM MinBias this is expected to be configurable,
  but it is the main silent-failure mode for this feature.
- A produced `TpMuon_*` table that is consistently empty, or suppressed by an
  order of magnitude relative to expectation, should be treated as a production
  misconfiguration first, not as a physics result.

Policy consequence for B4:
- After this fix, B4 is no longer a monolithic "all-noise" sample at the truth
  level.
- B4 becomes a realistic mixture of:
  - combinatorial / silent occupancy with no true muon,
  - real prompt pileup muons crossing the OMTF-relevant window,
  - decay-in-flight pileup muons from pion / kaon parents.
- Therefore some B4 windows become legitimate positive truth cases for the
  validity head. This is a physics effect, not a labeling bug.
- Any downstream training or validation plan that currently assumes "all B4
  targets must score low" has to be updated after the fix.

Validation consequences:
- Add a dedicated category for real pileup muons in the truth-accounting and
  dataset-policy notes:
  - in-time pileup muon
  - out-of-time pileup muon
- The B4 sparsity / flatness gate must be redefined accordingly. Post-fix, a
  nonzero positive-truth fraction in B4 is expected.
- The pilot closure should check:
  - `TpMuon` multiplicity per event / BX after the selection cuts,
  - in-time vs out-of-time composition from `TpMuon_bunchCrossing`,
  - displaced / decay-in-flight fraction against minbias expectations,
  - consistency between `reg_stub_tpId` occupancy and the persisted `TpMuon_*`
    table.

Pilot acceptance criteria:
- `TpMuon_*` table present in the pilot ROOTs.
- `reg_stub_tpId` present and populated where pileup-muon truth exists.
- No semantic change to old hard-scatter labeling through `reg_stub_trackId`.
- Observed pileup-muon rate closes at order-of-magnitude level with minbias
  expectations for the chosen `pT` and `eta` cuts.
- A near-empty `TpMuon_*` table in B4/G2/G4 should fail the pilot pending a
  mixing-configuration audit.

KNOWN CAVEAT: `TpMuon_dxy` is NOT the gun's true (curvature-consistent) d0
======================================================================
Finding (validated on G4_neg pilot, 2026-07-13):
- `TpMuon_dxy` is filled from `TrackingParticle::dxy()`, which CMSSW defines as
  the straight-line quantity `(-vx*py + vy*px) / pt`, i.e. `-vx*sin(phi) +
  vy*cos(phi)` evaluated at the production vertex.
- The G-campaign displaced guns (`FlatRandomPtGunProducer2`, `VertexSpectrum =
  "flatD0"`, e.g. G3/G4: `MinDxy=0`, `MaxDxy=50` cm) do NOT place the vertex
  with that straight-line formula. They call `newVertexWithD0(...)`, which
  solves for `(vx, vy)` using the actual helix curvature (gyroradius from
  `qinvpt` and B field) so that the true closest-approach impact parameter of
  the curved trajectory equals the flat-in-`[-50,50]` cm target.
- Consequence: `TpMuon_dxy` (straight-line) systematically overshoots the
  nominal `[MinDxy, MaxDxy]` window, especially for low-pT muons (dominant in
  the flat-1/pT spectrum), because the straight-line approximation is only
  accurate when the track curvature is negligible.
- Directly observed on a 20-event `G4_neg` local pilot: 4 of 13 hard-scatter
  signal muons had `|TpMuon_dxy| > 50 cm` (up to ~67 cm), all at pT in the
  2-9 GeV range.

This is NOT a production bug. `TpMuon_dxy` is the standard CMSSW
`TrackingParticle::dxy()` convention and is kept as-is for comparability with
other analyses. The caveat is about interpretation, not correctness of the
persisted value.

Required actions for anyone consuming `TpMuon_dxy`:
- Do NOT assume `TpMuon_dxy` is strictly bounded to `[MinDxy, MaxDxy]` for a
  given dataset. Treat the nominal gun range as a target for the TRUE
  (curvature-consistent) displacement, not a hard bound on the persisted
  branch.
- Any flatness / coverage check on `TpMuon_dxy` (e.g. dataset QA, training
  target normalization) should either:
  - bin/condition on `TpMuon_pt` before judging flatness, or
  - treat overflow beyond `[MinDxy, MaxDxy]` as expected low-pT smearing, not
    a generation failure.
- If a strictly curvature-consistent d0 branch is ever needed (e.g. to
  directly validate gun flatness, or as a cleaner regression target), it is
  not free: it requires either persisting raw `TpMuon_vx`/`TpMuon_vy` (cheap,
  unambiguous) and reconstructing the helix-consistent dxy downstream using
  `TpMuon_charge`, `TpMuon_pt`, `TpMuon_phi` and the known B field, or adding a
  dedicated in-producer branch (e.g. `TpMuon_dxyHelix`) computed the same way
  `FlatRandomPtGunProducer2::newVertexWithD0` does internally.

UPDATE (2026-07-13): implemented and validated.
- `TpMuon_vx` / `TpMuon_vy` (raw production-vertex transverse coords, cm) are
  now persisted in `OMTFAllInputTree`.
- `TpMuon_dxyHelix` is now persisted too: the curvature-consistent impact
  parameter, computed exactly the way
  `CandidateSimMuonMatcher::MatchingResult`'s SimTrack-path constructor already
  does for non-PU samples (`rg = -pT/(0.003*B*q)`, `B = 3.811 T`, `center =
  (vx - rg*sin(phi), vy + rg*cos(phi))`, `dxyHelix = rg + q*|center|`), but
  applied to the TrackingParticle path used for PU200/minbias-mixed samples
  (G-series, B4), where `CandidateSimMuonMatcher` itself still only has the
  naive `trackingParticle.dxy()`.
- Validated on a 25-event `G4_neg` local pilot (14 hard-scatter signal muons,
  gun target `MinDxy=0`/`MaxDxy=50` cm):
  - `TpMuon_dxy` (straight-line): 1/14 muons with `|dxy| > 50` cm (up to 62 cm).
  - `TpMuon_dxyHelix` (curvature-consistent): 0/14 muons outside `[0,50]` cm
    (max `|dxyHelix|` = 44.9 cm).
- `TpMuon_dxyHelix` and `TpMuon_dxy` can differ in sign; this is a convention
  difference (charge/rotation sign), not an error — compare magnitudes.
- Both `TpMuon_dxy` (standard CMSSW convention, kept for comparability) and
  `TpMuon_dxyHelix` (gun-consistent truth) are now available side by side; use
  `TpMuon_dxyHelix` for any flatness/coverage QA or as a regression target.
- Separate, NOT fixed here: `CandidateSimMuonMatcher::trackingParticleIsMuonInBx0Displ`
  (the TP selection filter used for candidate matching, not for `TpMuon_*`
  persistence) still branches on the naive `trackingParticle.dxy() < 30`
  threshold. This may bias matching-efficiency studies for low-pT displaced
  muons the same way; flagged for a future fix, out of scope for this note.

PILEUP CLASSIFICATION IN TpMuon_* TABLES
----------------------------------------------------------------------

Effective 2026-07-13 production launch:
- `TpMuon_isPileup` (uint8): 1 if pileup-originated (eventId ≠ 0), 0 if
  hard-scatter (eventId = 0).
- `TpMuon_isInTime` (uint8): 1 if in-time bunch crossing (bunchCrossing = 0),
  0 if out-of-time (bunchCrossing ≠ 0).
- `TpMuon_originClass` (int8): encoded PU classification:
  - 0 = hard-scatter, in-time (eventId = 0, bunchCrossing = 0)
  - 1 = pileup, in-time (eventId > 0, bunchCrossing = 0)
  - 2 = pileup, out-of-time (eventId > 0, bunchCrossing ≠ 0)
  - 3 = other/anomalous (rare; used for edge cases)
- `reg_pu_nTpMuonInTime` (int, scalar, per processor window): count of
  TrackingParticle muons in the current event/window that are PU in-time
  (TpMuon_originClass == 1). Useful for occupation studies.
- `reg_pu_nTpMuonOOT` (int, scalar, per processor window): count of
  TrackingParticle muons that are PU out-of-time (TpMuon_originClass == 2).

Use these branches for:
- Analyzing L1 trigger response to different PU categories (in-time vs
  out-of-time).
- Validating pileup mixing: histograms of occupancy by BX should match the
  configured PU spectrum.
- Tuning OMTF rate and efficiency separately for in-time and OOT PU.
